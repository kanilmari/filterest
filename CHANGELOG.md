# Changelog

All notable changes to Filterest are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

**Where this history starts.** Filterest has been released from this repository
since 9.3.3, and that is where this file begins. Earlier versions were released
from the shared version line of the private maintenance shell, and their history
stays there. Each entry below is the product part of that release; the newest
release is also described in
[RELEASE_NOTES.md](app/docs/publication/RELEASE_NOTES.md), which every release
overwrites.

Dates are the local (Europe/Helsinki) date on which the version was published.

## [Unreleased]

- **A dataset keeps its columns in the order they were written** — Creating a dataset sent its columns as unordered maps, so the new table's columns and its image table could come out in another order than the form showed. Creation now takes one ordered column list (`column_list`) through the whole creation, including the image table, and the old `columns` and `column_card_roles` maps are refused; the creation form, the agent tools and the browser-test helper send the new list.
- **Handovers follow the reporting format** — A handover printed by `db_report handover latest` opened with a heading larger than its worklines, and a workline's heading showed its status and phase but not its number. Each workline is now a second-level heading with its title, workline number and exact phase, such as `## Reporting — WL141 — 4`; the handover's title is bold text above them, and a paused, closed or archived line names its state under its heading. Stored handovers are unchanged and print in the new form.
- **The automation account never counts as an administrator** — The API-only automation account, which no person can sign in with, counted as a login-ready administrator: the first-run setup form could close because of it, the setup tool could skip creating the first administrator's password, and administrator recovery and creation counted it among the administrators. The user authentication screen could also re-enable a revoked automation account. Now one definition of a login-ready administrator leaves automation accounts out; administrator recovery, administrator creation, the first-run form and the setup tool read it, and the user authentication screen refuses an automation account before changing anything. The administrator recovery tool therefore needs database 9.7.15 or newer, the first that marks the automation account.
- **Language-key sources stay current in a composed installation** — When a private maintenance shell runs Filterest from a checkout outside its own folder, the start-up scan of where language keys are used was refused, so the record of each key's uses went stale. It now scans that checkout and records its files under the same `app/…` paths as a standalone installation, while the shell's own extra source folders must still lie inside the shell. A source folder or file linked outside its root now stops the scan before anything is saved, instead of leaving part of the code unscanned.
- **Browser tools and the shell agree on the project folder** — The browser tools' rule for where the project folder begins existed twice and treated links and marker files differently from the shell and Python tools. One module now holds it: links are followed to the real folder, marker files must be regular files, and a missing path no longer stops a tool.
- **A worker run bills the signed-in subscription unless `--api` is given** — `./worker_agent` now starts Codex or Claude without API-key variables, stops instead of quietly billing an API key when the client is not signed in with a ChatGPT or claude.ai subscription, and records the billing in the run's status and log. A `--background` run now leads its own process group (it is refused where `setsid` is missing) and is reported as started only once it is running or has already succeeded; a start not confirmed within 15 seconds is reported as unconfirmed, without any signal. `--stop` ends the run's process group with TERM and then KILL, confirming before every signal, from the leader's recorded start time, that the group is still the run's; a process that leaves the group by starting its own session is outside that guarantee.

## [9.3.21] - 2026-10-04

- **Database 9.9.2** — Version 9.3.21 pairs with database 9.9.2, which the update reaches from 9.9.1. 9.9.2 changes no table: it adds the second version of the missing-media check's setting and its texts, below.
- **A card's picture follows one rule and is no longer lost** — A card's picture could be the only reference to a picture file that was still on disk. Uploading a new picture overwrote that reference, and deleting the new picture then emptied it, so the card lost its picture for good although the file stayed on disk; this is how one site's About page lost a picture. And an upload made itself the card picture, while the next change in the gallery chose again by another rule, so a card's picture could switch back by itself. Now one rule chooses the card picture everywhere: the picture marked as the main one, otherwise the gallery's first. A new picture — an upload, a library picture, a linked, restored or automatically added one — goes to the end of the gallery, so it becomes the card picture only on a row that has none. A card picture the gallery does not hold stays until an administrator clears it when it cannot be kept elsewhere (a picture in another row's folder, an external address, a library picture); a picture in the row's own folder is kept as the first gallery picture, without copying the file, before a main picture replaces it, and taking the main mark away brings it back. The card picture field can only be cleared by hand. After the update, the application brings cards whose picture the old rule chose to the new rule when it starts, and finishes any it could not reach at later starts: such a card shows the main picture or the gallery's first instead of the newest upload. The article lists the gallery in the same order as the card, a picture that only the card shows appears first in it without editing actions, and fifty attachments can no longer hide the card's picture. The article opens on the picture the card shows, chosen by the card list's rule, so a dataset's own image field comes first there too; a library picture or a gallery the viewer may not open is left out of the answer. The article starts on that picture even when the row's earlier picture is still in the gallery, keeps a picture the viewer browsed to while the gallery still lists it, tells pictures apart by their whole address, and reads a multilingual picture value in the viewer's language. A stored picture name followed by a version or anchor, such as `?v=1`, now loads from its row's folder on both the card and the article. A file whose presence cannot be checked, for example on an unmounted disk, is never taken for a missing one, while a library picture whose file is certainly gone counts as none. Two changes to one gallery at once wait for each other, so a deleted picture can no longer stay on the card. A CSV restore never writes over a picture the rule keeps, not even with an empty cell: it keeps the stored picture and names the conflict in the server log. Editing a gallery row's file refreshes the card at once, moving a gallery row to another row refreshes both, and deleting a gallery item no longer moves into deleted storage a file that the same row's other pictures or its card picture still use.
- **Storage cleanup never touches the shared picture library** — The administrator routes that archive and prune unknown storage folders treated every folder not named by a dataset number as unknown, including the shared media library, the service catalog logos and the disk's own lost+found folder, so running them would have moved the whole library into deleted storage and then removed it. They now consider only folders named by a dataset number.
- **The missing-media check samples a whole dataset, notices updates and speaks every language** — The check that reports pictures and attachments missing from disk read the same oldest rows of a large dataset every time, ran at every server start, and showed part of its screen in English or as raw keys. It now runs by itself once after every update, when the application's or the database's version changes, and no longer at every start: the update moves every site to that, while keeping the site's other stored choices, and a site that switched the check off keeps it off. A large dataset is sampled evenly from its oldest to its newest row, or at random with a recorded seed, and a small one is read in full, page by page. It counts rows only up to a limit and estimates beyond it, stops within its time limit, and lists the datasets it could not reach instead of failing silently; a failed or interrupted run is saved too, and an unreadable setting falls back to the defaults with a notice instead of an error. It now also reads every card picture and picture field, and reports the card pictures whose file is missing, those it could not check and those kept from another row's folder; they share the run's row limit, with a fifth kept for them. A file is listed as unused only when every gallery and every picture field was read in full, because a card can show a file no gallery row names. The screen on the media tools page shows every setting with its allowed range, who started the last run, the application and database versions, notices when a limit cut the run short, and a per-dataset table. All of its texts are language keys in Finnish, English, Chinese and Cantonese.
- **A row counts as your own only when the dataset says who owns it** — A rule such as "must be approved unless the row is your own" guessed a row's owner from its creator column, its user column or, failing both, its row number, so a person whose user number matched a row's number counted as that row's owner. The owner now comes only from a dataset's named owner column, and only when the database confirms it is a real link to the users table; the users table and the service catalog keep their own. A dataset without such a column gives no own-row exception, so its unapproved rows show only to administrators. A field marked to hide on the article card unless the row is one's own now stays hidden whenever the owner cannot be established.
- **Signing in survives a browser update** — After a browser updated itself, signing in could stop at "Invalid CSRF token. Reload the page." on every site, and every site had signed the person out. A session that replaced one the server could not read was saved without the session cookie's settings, so the browser filed it under the folder of the request, such as `/api`, beside the site-wide one and from then on sent both; the browser could also show a stored copy of the sign-in page whose token had gone stale; and the browser's fingerprint contained its version number, so an update looked like another browser. A replacement session now gets the same cookie settings as every other session, and a second session cookie under such a folder is cleared while the site-wide one is kept. The sign-in page and its token are never stored by the browser. When a sign-in, verification-code or password-reset request from the sign-in page or the sign-in window meets a stale token, it fetches the session's current token and tries once more, keeping what the person typed. The fingerprint leaves version numbers out, and a signed-in session whose browser no longer matches now ends in one clean sign-out instead of passing the person back and forth between the sign-in page and the application. Because the fingerprint changes, the update signs everyone out once.
- **A dataset opens in the view its address names, otherwise in its default** — A dataset whose default view was the card view sometimes opened as articles, because the browser remembered the view and the open article from an earlier visit, and that memory came before the dataset's default. A newly loaded page now shows the view its address names, otherwise the dataset's default, and it forgets the articles left open on earlier visits, while sorting stays. A view chosen during the visit is kept until the page is loaded again, also across signing in.
- **Each browser tab keeps its own view and open article** — With the same site open in two browser tabs, opening a new tab or choosing a view in one could close the article that was open in the other, or change its view, because every tab of the site shared one memory of the view and of the open row. Each tab now remembers its own view and the row it has open, so nothing one tab does opens or closes an article in another; sorting, filters and paging stay shared by all of the site's tabs. Reloading an article's page brings back its related-rows tab, whether the related rows were open, and the scroll position. A link straight to an article opens even when the browser refuses a tab memory of its own; such a tab then keeps its view and open row only until the page is loaded again. A duplicated tab starts from a copy of the original's memory, and the two go their own ways from then on. A view or open row that an earlier version stored for all tabs is no longer read.
- **A row's address no longer puts the row's title into the page** — The server writes the browser tab title and the link-preview title into a page before anything is authorised. For an address that named a row, it read that row's title straight from the database with no rights check and no row rule, for any dataset not marked hidden, so a person who could open the site could read the title of a row they may not see, such as an unpublished service or a user's full name, by trying row numbers. On a site that requires signing in, a visitor who had not signed in was sent to the login page first and saw nothing. A row's address now carries the dataset's own title; the application still shows the row's title once it has read the row with the person's rights.

## [9.3.20] - 2026-10-02

- **A Docker installation starts from a folder whose files were created private** — A folder cloned by someone whose system makes new files readable only by their owner could not start in Docker. The database container runs its first-start scripts as its own user, which could not even list them, so the database never became healthy and Docker said only that; and the application's image copied the same private permissions, so its user could not run the program's start script. The Docker command now makes the two folders the database reads readable to it, only when something in them is not, and says so; the image makes its own copy of the program readable by its user and writable by no one, whatever the folder's permissions were.
- **`./filterest update` updates a Docker installation too** — The updater accepted only the two native kinds of installation, so the Docker installation the README recommends first had no supported way to reach a new release. The same command now updates it with the same safeguards: it checks that the release is published, stops only the application, backs up the database through the database's own container and reads that backup back before trusting it, keeps copies of the uploaded files and the protected settings, moves the folder forward to the release, and rebuilds with the release's pending database changes. It reports success only when the running application answers that it is the new version, that its database is compatible, and that it is this installation. If the new version does not become ready, its application is stopped while the database and the backup are kept, and the README shows how to return to the previous version, and how a Docker installation whose own updater predates this makes the move once by hand. A folder that claims to be both a native and a Docker installation, or a shell setting that would silently replace one of the installation's own Docker settings, is refused before anything changes, and only one update runs at a time.
- **An update's backup keeps who may read what** — Before an update changes anything, `./filterest update` backs up the database. On a native installation that backup left out the database's access rights, so a site restored from it would have lost what the application's limited database roles, the ones used for visitors, guests and read-only tools, are allowed to read, and pages would have failed until someone granted those rights again by hand. The backup now keeps them, as the Docker installation's backup already did; both are written with the same options, stated in one place. It still leaves out who owns each object, so it restores into a database of any name. A restore that should not bring the rights along can still leave them out, whereas rights missing from a backup can never be brought back.
- **`./filterest start` starts a Docker installation instead of beginning a native one** — In a folder prepared with `./filterest docker setup`, `./filterest start` did not recognise the Docker installation and began the native guided setup, which offers to install host packages and a PostgreSQL server beside the containers, and `./filterest status` reported on a native server that was not there. Start now starts the Docker stack and status shows its containers, while `./filterest setup` and `./filterest ctl --stop` stop at once and name the Docker command to use instead. A folder that records both a Docker and a native installation is refused by start, status and setup alike, by the same rule the updater applies, and the refusal names the files involved without showing what they contain.
- **Connecting two fields is explained in full, and its texts can be translated** — The dataset form's "Connect two fields" section read its button, information symbol and explanation from copy that no language key held, and it shared its column labels with the technical foreign-keys page, whose stored wording was older ("Referenced table"), so a site showed that wording in the form and a reader of Chinese or Cantonese saw English. The form now labels the two columns and the other dataset under language keys of its own, and the explanation says that the link runs from the referencing column of this dataset to the referenced column of the other, which is also known as a foreign key. All of it is stored in Finnish, English, Chinese and Cantonese, so an administrator can review and translate it where the rest of the interface is translated; the Chinese and Cantonese copy still awaits a translation review. The technical foreign-keys page keeps its wording. In the Manage table dialog of an existing dataset the information symbol no longer disappears from beside the section title: the form rewrote the title's text when it opened and wiped the symbol with it.
- **Database 9.9.1** — Version 9.3.20 pairs with database 9.9.1, which the update reaches from 9.9.0. 9.9.1 adds copy: the "Connect two fields" texts above, and the texts of the dataset form's folder, rights, picture, deletion-protection and link controls, which a new installation's package had marked as written without writing them. A new and an upgraded installation now end with the same texts, and a translation a site has already changed is never overwritten. It also carries the repair below. The tables are unchanged; the 9.9.1 schema snapshot differs from 9.9.0 only in the stated name of the link from column metadata to the dataset registry.
- **A stale display setting no longer fills the server log** — Sites installed from the public package, filterest.com and fintravel.fi among them, carried a setting telling the list of dataset views to show a column named view_name beside a reference, a column that list never had. The views already fell back to the right name, but the server wrote a warning each time it looked, and since 9.9.0 it looks on every read of the dataset registry. The 9.9.1 update clears any such setting that names a missing column, and gives the link from column metadata to the dataset registry the same name on every site, where the package had left the naming to PostgreSQL. A link of that generated name with any other rule stops the update rather than being renamed in silence. The package itself now states both correctly, so a new installation needs no repair.
- **A card's short description sits in the middle of its row, and keywords stand out** — On a Glowy card, a description of one line hugged the top of its box, because the box is as tall as its icon and the text was pinned to the top; a description of two lines looked right only because it was taller than the icon. The text is now centred against the icon whatever its line count, which also lines the icon up with its own frame. Keyword chips took the card's own colour at lower opacity, so in both themes they barely showed; they now take their own theme colour, `keyword_label_bg_color`, with one value for the light theme and one for the dark, on cards of both styles and in the article view.
- **The workline observatory searches the way every dataset does** — Searching the observatory for a workline's number listed lines whose text merely contained it, such as the address 127.0.0.1 or a commit hash, and never the workline with that number, because the observatory compared text with a substring search of its own instead of the dataset search. It now runs the one search every dataset uses, defined once for both: a plain number finds the row with that number first, a word is found by its beginning and any of the words is enough, and without a chosen order the matches are ranked by relevance, which the sort control now also shows. A word is no longer found by its middle, exactly as in a dataset. The board and its search read the same moment of the database, and the connection is released before the answer is sent.
- **The start log shows errors only for errors** — Every start wrote one line per route listing its processing stages, and because one stage is called error_handling, the log classed each of those some 240 ordinary lines as an error, hiding the real ones. The list is now a debug line, so an ordinary start shows only real errors. An error code inside a line, such as queue_claim_error, still makes that line an error.
- **Visitors can no longer write to the database, and no account can grant itself rights through the privilege views** — The database account the application uses for visitors could add, change and delete rows and advance number sequences, although no visitor feature writes anything, and the accounts of signed-in users could write to the views that edit database privileges and run the two functions behind them, which act with the owner's rights, so a signed-in account could have granted itself almost any right. A startup stage now takes these rights away on every start, after the database updates and before the first request, and compares what remains before and after: visitors only read, and no ordinary account can use the privilege views or those functions. Every other right stays as it was, and if the stage cannot finish, the application does not start. Narrowing the signed-in users' account to the tables it needs is the next stage.

## [9.3.19] - 2026-09-27

[GitHub release](https://github.com/kanilmari/filterest/releases/tag/v9.3.19) · Database compatibility moves from 9.8.1 to 9.9.0.
- **A sign-in now has a last moment it cannot pass** — A sign-in was renewed on every visit, so one used daily never ended; and around thirty places in the application write a session, several of them on routes reachable without signing in, each writing a fresh signature over whatever the session holds. Someone holding a copy of a session cookie could therefore keep it readable indefinitely and outlive the record of its own sign-out. Every sign-in is now given, at the moment it begins, the moment it ends: read from the database's own clock so a wrong clock on any one machine cannot shift it, carried inside the signed cookie where a browser cannot alter it, and never rewritten by any of those thirty places. The shared boundary that already refuses a signed-out sign-in refuses an expired one in the same question and against the same reading of the clock. The deadline is a moment and not a length, which is the whole of the design: comparing a sign-in's start against whatever the setting says today would leave the setting itself as a way to extend a sign-in — sign out under a one-day limit, keep the cookie signed through a public route, then raise the limit, and the same cookie is accepted again once its refusal record has run out. Changing the setting therefore governs sign-ins made after the change and never touches one already given, and a sign-out is remembered to the sign-in's own deadline rather than to a length recomputed at the time. How long a sign-in may last is one setting, `absolute_sign_in_limit`, holding whether the limit is on, the unit (hours or days, counted as elapsed time) and the amount; the default is thirty days, and it is seeded for an upgraded site and a new installation by the same file. A row that is missing or damaged gives that same default and says so in the log — never the permissive answer — while a database that cannot be asked is an error and never falls back to the application's own clock. Switching the limit off is possible but has to be said in the setting: such a sign-in is marked as having no deadline, and a sign-out of it is remembered for good. What this costs is that everyone signs in again once their limit is reached, whatever they are doing; unsaved text in a page is lost then, exactly as it already is when a session expires, and preserving it is separate work.
- **A long-running tool can sign in again after its sign-in ends** — With a ceiling on how long a sign-in lasts, a tool that runs for weeks can be signed out by the clock while it is still working. Its client remembered being signed in, so the failed call was followed by a sign-in attempt that answered "already signed in" from memory and every call after that failed too. The cached sign-in is now dropped when the server says it has ended, on both the ordinary and the file-carrying request paths. The failed call itself is not repeated, because a write that failed may or may not have been applied.
- **Signing out now sticks** — Signing out only expired the three cookies in the browser and the server kept no record of it, so a request that was already in flight in another tab finished afterwards, wrote all three back, and the person held working credentials they believed they had given up. Worse, the sign-out itself handed back a fresh one: the session store signs whatever the session still holds every time it is written, and telling the browser to delete a cookie does not stop that, so the reply to a sign-out contained a valid, newly signed sign-in good for another seven days. Each sign-in now carries its own unguessable identity inside the signed cookie, a sign-out writes that identity into one small table — no user, no address, no browser details — and every boundary that checks a sign-in refuses it from then on. The record lasts as long as the cookie could, is computed by the database's own clock, and is cleared by the next sign-out. This ends one browser's sign-in, not the account: signing out on a phone leaves the same person's desktop alone. Signing out is also a POST now, so another site cannot cause one, and it no longer saves the session at all, which is both why nothing is re-signed and why the audit record still names who signed out. Sign-ins made before this existed carry no identity and cannot be made to stay out, so they are refused once and the person signs in again — everyone signed in at the time of the upgrade signs in one more time. What this does not yet reach is written down beside the code: around thirty other places write a session, several on routes reachable without signing in, so someone already holding a stolen cookie could have it signed afresh elsewhere and outlast the record; the durable fix is a sign-in deadline stamped once and not extendable.
- **A piece of the session cookie is no longer written to the log** — Every sign-in and every renewal logged the first sixty characters of the Set-Cookie header, which is the beginning of the signed session value itself. Sixty characters fall short of the signature and so were not usable on their own, which is why it went unnoticed for so long. A credential does not belong in a log at any length, and the line is gone; a save that fails is still reported.
- **The three sign-in cookies renew together** — After 9.3.18 the two browser-binding cookies renewed on every request while the session cookie renewed only when something saved the session, which an in-application tab switch does not, so two moved while the third stood still, and a person who only ever navigated inside the application would have been signed out on day eight. One place now renews a used sign-in and re-emits all three cookies with the same fresh seven days, only after the request has proved it carries the binding its session stores, and the seven days is stated once where the store, the sign-in handlers and the binding writer all read it. An idle person still loses all three at once and is told; a foreign binding is still refused; signing out still ends all three.
- **A sign-in lasts as long on the server as the browser is told** — The session store is built with its library's thirty-day default, which is applied to the signature inside the cookie at that moment; setting the store's options afterwards changed only what the browser was told. The server therefore went on reading a session cookie for thirty days while the browser expired it in seven — and because a used sign-in is now renewed, a cookie kept elsewhere and presented on day eight was read and given seven fresh days. The age the server enforces is now the same one the browser is told, and a test reports what each signature check actually allows.
- **Twenty internal relationships an installed site was born without** — Filterest declares links between its own bookkeeping tables: which member belongs to which group, which permission applies to which dataset, which folder holds a dataset. Twenty of them were declared on a site that had grown over time and on the development database, but the install package shipped none, so every site installed from it was born without them. Two things follow: the database keeps a permission row pointing at a dataset that no longer exists, and the table view, which builds a readable companion column from each declared link, shows a bare number where it should show "admins" or a dataset's name. The twenty are restored by a migration that reproduces each link's exact name and exact behaviour when the row it points at is deleted — fifteen remove the dependent row, three clear the pointer, two refuse the delete — and the install package now ships them, so a new site starts correct. The migration is safe to run twice, passes over a link that is already there, and stops the whole update rather than proceeding if a link of the same name means something different or a row points at nothing.

## [9.3.18] - 2026-09-25

[GitHub release](https://github.com/kanilmari/filterest/releases/tag/v9.3.18) · Database compatibility 9.8.1, no migration.
- **Signing in works the same way in every environment** — A development server accepted a sign-in without the browser's identity check, giving every such session the same fixed device binding, and it kept an older, weaker form sign-in alive beside the current one. Both are gone: the identity check is always required, and the old form sign-in is refused everywhere, as production already refused it.
- **Creating a payment always requires its service token** — With no token configured, a development server authorized every caller, which is exactly the state a half-configured installation is in. It now refuses.
- **What development relaxes stays on the developer's own machine** — Automatic approval of a newly registered account, the exemption from the failed-sign-in limit, and the browser error log's write address now require both explicit development mode and a request from the machine itself; a development server reached over the network behaves like production. The insecure-proxy switch is ignored outside development, so session cookies keep their Secure flag. The error-log address also bounds what it accepts and strips control characters, so a caller cannot forge log lines.
- **A worker asks for full access instead of receiving it** — Codex workers run in the workspace sandbox by default, without the database, the network or the rest of the file system; full access is now an explicit choice per run.
- **A card's short text uses both its lines** — A stored text whose second line is empty, such as a heading followed by a blank line, left the card showing one line of text and one blank. The card's two-line view now skips wholly empty lines; the stored text is unchanged, and the article view and the edit form still show it in full.
- **The dataset's symbol is chosen from pictures** — The symbol was picked from a list of names, and the chosen symbol was drawn dark on a dark background, so the dark theme swallowed it. The picker now draws each symbol beside its name, with a search box, and the chosen symbol follows the theme's text colour. "No symbol" is still the one way to clear it, and the creation form no longer carries the previous dataset's symbol into the next one.
- **The browser tab says where you are** — The tab's title was written once, when the page was first loaded, so after moving to another dataset, changing view, opening or closing an article, searching, or stepping back and forward, it still named whatever was loaded first: on one site it read "Privacy policy" while the page showed travel deals. One place now writes the title at every such boundary, in the reader's own language, and a late answer can no longer overwrite a newer one.
- **An article view with no matches keeps its header** — Searching in the article view for something that matches nothing left the page with no dataset title and no search field, so there was no way back except the browser's own controls. The header's visibility now follows the view the person chose instead of an event that only an opened article could send, and an article view without rows can never send it.
- **A dataset is created through one route only** — A second, older address created datasets without choosing a folder, so its datasets landed in "database / other_tables" and stayed out of the site's navigation — the very way a new dataset went missing on fintravel.fi. Nothing called it, it existed only where an optional AI interface setting was on, and it is now removed with its handler and registry entries.
- **A card names a value only where the name helps** — A card printed every field's name on its own line above the value, so a long text spent one of its two lines on the word "Summary". A field's name now sits beside its value with a colon, such as "Price: 129 €", and a running-text field shows no name at all. The choice comes from the column, never from one row's text, so two rows of the same dataset always agree, and a column that states its own arrangement still overrides it.
- **"Connect two fields" says what linking two datasets does** — The dataset form offered "Add dataset reference" while the database and the technical page said "Add foreign key", so the same act had two names and neither explained itself. The form now says "Connect two fields", with an information symbol that opens one sentence: a row of this dataset points at a row of another one, so the other row's information can be shown and the value stays valid, with the technical term in parentheses. The technical foreign-keys page keeps its own wording.
- **The application notices when a picture's file has left the disk** — A row could point at a picture whose file was long gone, and nothing said so: the picture simply did not appear, as on one site's About page. A check now reads the pictures and attachments rows refer to and reports the ones that are no longer in storage. It only reports: it never repairs and never deletes. It runs in the background after startup and on demand from the media tools screen, within a row limit and a time limit an administrator sets, spread between datasets in proportion to their size so small datasets are always checked completely. The last result stays on the screen, with a plain notice when a limit stopped the run. Files that no row uses can be reported too, behind their own setting, off by default.
- **The emergency command can also create the first administrator** — It could only restore an account that still existed, which is no help to a rebuilt or restored site that has none. Behind its own switch it now creates one, on the server, in a protected terminal: it names the site, the database and the account before acting, says whether the ordinary repair path is still open, demands a typed phrase when an administrator already exists, asks for the password and PIN without echoing them, and writes the account, its group, its credentials and an audit entry in one transaction or not at all. It can only add an account, never change one. The browser's first-run form and this command now share one definition of what an administrator is, so the two cannot drift apart.
- **Every dialog keeps the same distance from the screen's edges** — Each dialog used to state its own margin, so on a phone one stood 24 px from the edges while the rule said 16, and the height had three different answers across the product. One rule now keeps 16 px on all four sides, and a dialog states only its own maximum size. The stacked dialogs are sized by one owner instead of two that disagreed; both are pixel-identical to before.
- **Code that nothing used is gone** — A text no screen showed, a spacing value with no readers, four functions only their own tests called, and the card view's replaced details printer. Each was checked for a real caller first, and the safety rules those tests guarded are proven on the paths that are actually used.
- **The space above a dataset's header icon is yours to set** — The icon sat 12 px below the dataset tabs, with no way to change it. It now starts 40 px below by default, and an administrator adjusts that distance in the appearance palette under "Dataset header"; the page follows the slider without a reload. One named value carries it, so the stylesheet states the distance once and a site that never touches the setting still gets the new default.
- **An AI provider's key can be installed from the embeddings page** — Only one provider's key could be entered in the interface, and the other had to be written into a settings file on the server. The embeddings page now says whether a key exists for the site's chosen provider and, when none does, offers a field for it: what is sent to the provider is stated beside it, the key is written into the installation's protected settings and used at once, and it is never shown, echoed or logged again. Where an installation keeps its settings outside the application, the page says exactly that and changes nothing.
- **Every card renderer places a field's name the same way** — The rule that puts a short value's name beside it, and leaves a running text's name off, reached only one of the card's four renderers, so a detail tile still printed the name as a heading above the value. All of them now ask the same question in the same place, and the answer comes from the column rather than from the row being drawn. A card is shorter for it, and on a phone a field's name is no longer cut off in the middle.
- **The address says which view you are looking at** — Closing an article left "view=article_view" in the address, and the next search, sort or filter copied it onward, so a bookmarked or reloaded address reopened an article the person had left. Which view is showing was remembered in three places that could disagree. One of them now decides: after a view has finished rendering, the address and the remembered parameters are written together from what is actually on screen, including when a permission gives the person a different view than the address asked for. An article view with no rows keeps its own name, because that is a real state.
