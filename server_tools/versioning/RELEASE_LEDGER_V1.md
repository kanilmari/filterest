# Filterest release ledger contract v1

The ledger preserves per-build history without treating a changing root version
file as the source of truth. Version 1 is intentionally local and offline: it
does not contact GitHub, mutate a database, publish a release, or install an
update.

## Files and authority

- `release_ledger.v1.jsonl` is the append-only history. It starts as a zero-byte
  file; no Filterest 8.29.4 history is inferred or backfilled.
- `release_ledger_record.v1.schema.json` defines each JSONL record.
- `build_identity.v1.schema.json` defines generated `BUILD_IDENTITY.json`.
- `release_contract_v1.py` enforces JSON schemas' structural rules plus the
  cross-field, byte-level, hash-chain, and uniqueness rules.

`VERSION_APP` may remain a current-version convenience pointer, but it is not
historical authority under this contract.

## Classification

- `channel` is `development` or `stable`. V1 has no nightly channel.
- `artifact_type` is `runtime` or `backup`. A backup is never an update-feed
  release.
- `maturity` is `snapshot`, `candidate`, or `published`.

Development artifacts and backups must be snapshots. Candidate and published
artifacts must be stable runtime artifacts. Publication still requires a later
GitHub Release manifest; a ledger value cannot by itself prove remote
publication.

## Byte and hash rules

Each record is UTF-8 canonical JSON with sorted keys, no insignificant
whitespace, and exactly one trailing LF byte. Blank lines, CRLF, a UTF-8 byte
order mark, unknown fields, and a missing final LF are invalid.

The first record has `previous_record_sha256: null`. Every later record stores
the lowercase SHA-256 of the preceding record's exact bytes, including its LF.
Record IDs, build IDs, and published stable application versions are unique.

For append-only validation, the complete previous ledger must be an exact byte
prefix of the candidate ledger. Corrections and withdrawals must therefore be
new record types in a future schema version, never edits to v1 history.

Validate the current file in isolation:

```sh
python3 server_tools/scripts/validate_release_ledger.py
```

Validate a candidate against an earlier committed copy:

```sh
python3 server_tools/scripts/validate_release_ledger.py \
  path/to/candidate.jsonl --previous path/to/previous.jsonl
```

Append one explicitly classified build after validating that prefix:

```sh
python3 server_tools/scripts/append_release_ledger_record.py \
  --ledger path/to/release_ledger.v1.jsonl \
  --previous path/to/previous.jsonl \
  --app-version 8.30.0 \
  --artifact-type runtime \
  --channel stable \
  --maturity candidate \
  --source-model public_first \
  --source-commit 0123456789abcdef0123456789abcdef01234567 \
  --db-min-version 8.0.59 \
  --db-target-version 8.0.59 \
  --created-at 2026-08-16T12:00:00Z
```

Every argument is explicit. Repeating exactly the same command is idempotent;
reusing its build ID with different immutable data fails closed.

## Build identity generation

`BUILD_IDENTITY.json` is derived only from one validated ledger record. The
generator copies immutable fields and binds the identity to the SHA-256 of the
exact ledger line; it does not infer a channel from a branch or version file.

```sh
python3 server_tools/public_slice_export/generate_filterest_build_identity.py \
  --ledger path/to/release_ledger.v1.jsonl \
  --record-id build:filterest-8.30.0-stable-runtime-0123456789ab \
  --expected-app-version 8.30.0 \
  --expected-db-version 8.0.59 \
  --output path/to/BUILD_IDENTITY.json
```

The generated bytes are deterministic for a given ledger record. A future
release manifest will bind these bytes to an immutable public commit and GitHub
Release; that remote integration is outside the v1 foundation.
