# Frontend Guide: Results, Cards and Articles

Part of the [Frontend Guide](Frontend_Guide.md). Section numbers continue those of the former single-file guide, so older references to them stay valid.

## 1. Showing Results in Different Views

Row support for listings and streamed/blocking search is owned by the server ([row_response_support.go](../../backend/core_components/dynamic_table_tools/dtt_1_row_crud/dtt_1_row_read/row_response_support.go)): `view_key=card|article_view|product_card` requires picture support, `view_key=map` requires permitted geometry. Article aliases are normalized. Legacy `include_card_support=1` / `include_map_support=1` add support; zero never disables a projection's requirements. Missing/other views request no rich support unless flagged. Picture and geometry support is intersected with the caller's readable columns before projection or enrichment, including Home's card delegate. A denied optional support read preserves authorized rows and omits that value; parent picture values are never retried through the owner connection. Support leaves presented columns unchanged and cached gallery pictures remain authorized even without enrichment.

Browser row callers send only the explicit projection (`view_key`), never support flags; legacy flags remain a server API compatibility contract. Refresh and deep-linked row previews send their current normalized view. Listing reloads and later pages retain the committed list's projection when available, otherwise use the current view. Main intelligent-search streams send their request's view; compact supplemental searches, permission-editor reads and translation repair explicitly use `table`, preserving their existing fields without requesting rich support. Expanded articles and Image First Article View history restoration independently request `article_view`. Home continues to delegate with `card`. A retained navigation list is not authorized article content: transferring it preserves its projection, rows and raw offset, while opening a selected article still fetches that row independently.

### Overview
1.  **Search**: The user submits a search query. `do_intelligent_search()` sends a request to `/api/get-intelligent-results` and streams results.
2.  **Backend**: `GetIntelligentResultsHandlerWrapper` returns matching records in two stages (text and AI). The request carries the interface language as `lang`, the reader's language: the AI stage searches every stored embedding, general and per language, and only ranks a match in the reader's language slightly ahead.
3.  **Notices**: When the text-search stage finishes, a `text_search_ended` notice is inserted. If the AI stage returns suggestions, a `see_also` notice appears.
4.  **Rendering**: `filterest/app/frontend/core_components/table_views/dataset_view_printer.js` renders the data using the selected view module.
5.  **Filters**: The global search term appears as an `.active-filter-item` above the results.

How a full first-page response resolves category selections, and the category panel shown before the results, are described in [Category panel and dropdowns](Frontend_Category_Panel_And_Dropdowns.md).

### View Types

The selector's product-owned names come from `dataset_view_registry.js`.
Startup synchronizes the Finnish, English and Chinese texts for Cards, Article,
Table, List, Compare and More, and for the More options Ticket, Product card,
Calendar, Map, Settings, Cloud management and Tree. These keys deliberately
replace older installation wording such as "View calendar"; other language keys
are untouched. `dataset_view_registry.test.js` checks every startup seed against
the registry to prevent drift. Chart keeps its separate fallback-only `view_chart`
key for the rename reason described below.

In development, the **Locked layout / Free layout (beta)** selector appears in
Cards and Article, including legacy Article addresses. Locked layout selects
the standard card renderer; Free layout selects the experimental renderer for
the result cards, also used by Article's result navigation. The per-dataset choice
lives in this browser's localStorage. The persistent view selector updates it on
view switches and history restoration, and closes/removes its menu on leaving
these views. The existing development-only availability check also disables the
experimental renderer in production. Calendar and the other renderers do not
read this choice and do not show the control.

-   **Card View**: Presents each record as a card. Suitable for rich media. Implemented in `filterest/app/frontend/core_components/table_views/card_view/card_view_printer.js`.
-   **Table View**: Displays results in rows and columns. Good for comparing fields. Implemented in `filterest/app/frontend/core_components/table_views/table_view/table_structure_builder.js`.
-   **Tree View**: Organizes results hierarchically. Helps explore nested relationships. For ordinary datasets it uses row-level `id` + `parent_*` data; for the database catalog datasets (`system_table_folders`, `system_db_tables`) it reuses `/api/tree_data` so folders include their table leaves. Implemented in `filterest/app/frontend/core_components/table_views/tree_view/tree_view_printer.js`.
-   **Chart / Kaavio** (`price_chart`): A general time-series chart, including tracking numeric `id` growth. The selector offers it only when delivered column metadata includes at least one scalar date, time (with or without timezone), or timestamp (with or without timezone), and one scalar integer or numeric column. Text dates, arrays, intervals and unrecognized types do not qualify; row count and group permissions do not decide fit. Chart access is staged per group through the table-independent permission `ui.view.price_chart` at `/ui/view/price_chart`. Startup reconciliation creates the route and the administrator safety net grants it to the administrators group. Other groups, including users and guests, need an explicit grant before Chart appears in the selector or opens through an address. A dataset or site Chart default does not bypass this grant; a denied Chart falls back to an ordinary reading view. Existing non-administrator groups without this grant lose Chart until an administrator enables it. An unsuitable chart address opens a permitted fallback view with a translated explanation and view choices.
    Only readers with the Chart grant see the fit explanation. When the fallback needs its own listing projection, the refresh carries the original Chart request as temporary render context so the second build retains the explanation. The chosen view and settled address describe the fallback; this context is not saved and ends with that refresh.
    Axis pickers sit below the hero, including on fitting empty tables. X choices are usable time columns; Y choices are numeric columns, including `id`. Inference prefers a typed time alias, then the first temporal column; a typed price-like alias, then the first other numeric column, then numeric `id`. `chart_x` and `chart_y` name physical columns in the shareable address; each invalid or unavailable value falls back independently. Address choices override administrator defaults, which override inference. These parameters stay in page memory, alongside the view, and never become row filters or another tab's settings. Back/Forward preserves them.
    Administrators save the dataset default through the existing site field-set save API and its administrator, dataset-read and delivered-field checks. The chart's site assignment in `system_view_field_set_assignments` points to the shared `price_chart_axes` collection in `system_column_field_sets`; saving writes ordered members `[x, y]`, but reading selects the eligible temporal and numeric members by type because the API removes inaccessible fields and compacts the list. If one member is missing, only that axis falls back to inference. Chart reads the site collection explicitly, rather than treating personal/group field visibility as axes. Saving leaves group assignments and other collections intact. The registered `system_table_views` key remains `price_chart`, so old addresses keep working; Chart now has its own permission identity for group staging. No migration is needed: startup reconciles the route and existing ordered field sets already hold this configuration; the new `view_chart` language key supplies Kaavio / Chart / 图表 / 圖表 through local fallbacks without an installation's old price-label translations masking the rename. Rendering and fit live in `price_chart_view/`; `C_card_view/C15_chart_axes.spec.ts` is the card-project browser proof.
-   **Other Views**: Register view keys, labels, container suffixes, selector groups, and UI permission routes in `filterest/app/frontend/core_components/table_views/dataset_view_registry.js`; keep concrete renderer imports and row-commit policies together in `filterest/app/frontend/core_components/table_views/dataset_view_renderer.js`. The dataset view printer assembles the page around that dispatch. Listing reloads and pages use `commitDatasetViewRows` through the scroll loader's `appendDataToView` delegate: replacement clears old rows even when empty; append retains the loaded prefix, and empty append is inert. The boundary guards the chosen view and exact connected host across asynchronous work. Missing or abandoned surfaces cannot advance offsets or retained rows. Table bodies and normal/transposed/ticket components use their existing set/append paths; card/article replacements build off screen and swap once, retaining controls and disposing abandoned resources (WL103). Row trees retain expansion/search/focus across row and language rebuilds: initial opening applies only to new branches, retained descendants keep their own expansion under collapsed parents, and clearing search restores the pre-search expansion plus new branches' opening defaults. Expansion and folder counts finish inside the awaited tree commit, before an accepted reload reconnects scrolling or a final page stops it; only the selection notification is deferred. Calendar retains mode/date and language sources, chart append retains zoom, and settings append retains edited inputs and their save owner. Catalog trees/cloud operations use independent endpoints. Product cards own their committed raw rows: replacement builds once and swaps the cards (including an empty result); append adds only unseen string-normalized row IDs with their pictures while retaining existing card nodes. Language refresh uses that current row list, including later pages, and the same guarded root refuses abandoned commits. Map retains current initial output until WL162 batch 5. Pagination owns string-ID deduplication, raw server-row offsets and remembered projections in `dataset_loaded_rows.js`; retained article navigation keeps its original projection and articles fetch their own permitted content. The outer `.scrollable_content` host owns scrolling (`styles/base.css`); fresh dataset/view surfaces reset both axes synchronously after the populated swap has mounted category controls and restored the scrolling hero in `dataset_view_printer.js`, before paging starts. Its `data-view` marker changes only on commit. Restored control focus uses `preventScroll`. Repeated toolbar visibility updates keep the first dismissal deadline, so its collapsed border cannot disappear later and shift a category popup after a phone page is resized. Same-view refreshes, category replacements and page appends keep the viewport; mounted dataset tabs and classic article/history returns retain their existing snapshots. `Q_scroll/Q2_offset_reset.spec.ts` checks the visible destination, new surfaces and retained article returns on every card project; its article proof dismisses with browser Back on phones at widths ≤700 px and the visible close control on tablet/desktop, then checks Forward/Back for the retained position and the same mounted card node; `G_navigation/G7_dataset_scroll_retention.spec.ts` checks retained tabs and logical anchors.

List and comparison views use the same `TableComponent` selection and copy
menu. Mouse users select a range and right-click a selected cell. Touch users
hold a data cell to select it and open that menu; holding an already selected
cell preserves its range. Movement, touch cancellation and component disposal
cancel pending holds. `table_component_touch_copy_controller.js` owns the
gesture and joins the existing component teardown; menu labels, clipboard
payloads, themes and viewport clamping keep their shared implementations. The
controller records the native Touch identifier separately from the pointer id
and cancels only that completed hold's `touchend` in a non-passive listener.
This stops compatibility mouse presses and clicks at their source, including
clicks that would hit the menu after it moves into the page body. Other releases
remain uncancelled. As a fallback, suppression after release requires the held
touch's pointer identity or an explicit
browser touch-origin marker, matching position and a short release window;
each compatibility event is consumed once. Completion, expiry, a new press or
disposal retires that state, so keyboard requests, mouse right-clicks and later
taps can use the same cell again.

### Where a Dataset's View State Lives
Each browser tab keeps its own view and open row, so one tab never changes or erases another's (owner decision K143, 3.10.2026):
-   **This tab only** (`sessionStorage`): the view a dataset shows, read and written only through `filterest/app/frontend/core_components/state_stores/dataset_view_choice_saver.js`, and the row the article or card view holds open, the `articleView` and `cardView` parts of `getUnifiedTableState`/`setUnifiedTableState` in `filterest/app/frontend/core_components/state_stores/table_state_store.js`. The view in a dataset's cached address parameters stays in the page's memory (`query_params.js`).
-   **A browser that refuses session storage** keeps that view and open row in the page's memory instead (`filterest/app/frontend/core_components/state_stores/tab_session_storage.js`), so a deep link still opens its article and a chosen view still reaches the redraw. Sign-out forgets this memory together with the cached address parameters (`clearClientAuthArtifacts` in `logout_shell_reset.js`).
-   **Every tab** (`localStorage`): sorting, filters and paging, through the same table state store.
-   The readable dataset catalogue (`GET /api/datasets`) returns `table_uid`, `dataset_name`, `names` and `preferred_name` alongside existing navigation metadata. `dataset_access_registry.js` owns the page-memory snapshot and private name/uid indexes; `resolveDataset({name})` / `resolveDataset({uid})` distinguish `found`, `unknown` and `not_ready`. Bootstrap primes it for guests and signed-in users before deep links and URL query parameters are interpreted. Alias saves and returning to a live page force a catalogue refresh; empty successful lists replace old names, failed refreshes preserve both accepted names and ordered tabs while remaining retryable, and identity/permission resets reject earlier responses. Back/Forward waits for hydration and restores the entry still current at that point. Request ordering and accepted-snapshot validity are separate. `dataset_aliases.js` retains only compatibility delegates: it performs no independent fetch, prefix inference or built-in name fallback. Its retained refresh helper returns the former immutable `{rawToPublic, publicToRaw}` maps, derived only from the accepted readable catalogue. The global `/api/dataset-aliases` route is retired; the administrator editor uses its separate administrator-only management endpoint. Saved catalogue tab order is filtered through readable identities, preserves supported static tabs explicitly and renumbers positions without gaps. This catalogue never grants backend request authority; raw API target normalization and retained old names are later naming slices. A fresh page shows the view and row its address names, otherwise the dataset's default: page load forgets the earlier visit's views and open rows in its own tab only (`table_loader_handler.js`). Reloading an open article's own address keeps its related tab and scroll position. A duplicated browser tab copies the session storage, so on the same row's address it keeps that position too; this is intended, and afterwards each tab's changes stay its own.
-   The catalogue uses the enabled row-read capability and the same explicitly enabled development administrator recovery mode as row requests. Administrator membership alone grants no normal catalogue access. Runtime consistency registration supplies the same enabled dataset-specific administrator grants as ordinary creation, inside the registration transaction. Every name published in a readable pool, including an active secondary alias, resolves to that same dataset for server document requests.
-   Server name pools and alias ownership use the stable dataset uid and retain the schema, so equal physical table names cannot mix aliases. Ownership is checked across all schemas before the catalogue and document routes select supported public-schema identities. Canonical links and sitemap entries use the accepted pool's preferred name too; a rejected primary alias cannot reappear in a generated address. Failed naming reads keep raw names and do not fall back to the legacy editor registry.
-   Namespace persistence belongs to migration `20261009000078`: every registry/alias write takes one PostgreSQL advisory transaction lock and advances an internal revision witness, so even a stale repeatable-read transaction refuses rather than claiming a name twice. Create and both rename APIs, primary alias save/clear, and dataset deletion acquire it before target reads or row locks. PostgreSQL statement/row triggers guard bypassing writes too. Dataset lookup first preserves exact canonical ownership, including legacy names differing only in case; non-exact lookup uses the same ASCII case fold as enforcement and refuses ambiguous owners. Pools compute `canonical_name_exact_only` across the global registry before permission filtering, so a readable subset cannot reinstate an ambiguous folded name. The browser keeps separate exact-canonical and folded indexes; unreadable exact names never fall through to a different owner. The administrator alias editor reports `disabled_aliases` with stable translated `reason_key` values; ordinary catalogues select only active aliases. Audit rows survive primary replacement and clear. Saving a normalized alias reactivates only an exact stored spelling; an invalid uppercase or space-padded audit row stays untouched while the normalized row is inserted. Text, dropdown/input placeholders and audit reasons use the existing language-renderer refresh without resetting alias or dropdown-search drafts. The editor preloads its stored interface-language dictionary through the shared translation request cache and passes that language to `getTranslationForKey`; a public-menu fallback to English cannot override existing Chinese/Cantonese or other site translations. Missing or blank dictionary values fall back to English, then the editor's authored copy if neither dictionary has text. Namespace refusals use `error_lang_key=dataset_namespace_conflict` (409), `dataset_namespace_invalid` (400), or `dataset_namespace_retry` (409 for a stale snapshot); the editor keeps the unsaved input and accepted preview after refusal. Former-name retention remains slice 5.

## 4. Asset / Media Surfaces

Shared asset-linking is now visible in multiple frontend surfaces, not only the admin capability view.

### Current End-User Surfaces
-   **Article View**: Existing rows can use `row_article_image_gallery.js` and `row_article_attachment_list.js` for image upload/delete/set-primary plus attachment upload/open/download/delete. PDF attachments should preview inline inside the existing article view rather than spawning a second modal on top. The article view's modules use the `row_article_` file prefix; its CSS classes still carry internal `big_card` identifiers.
-   **Add-Row Modal**: `gt_1_1_row_create/row_relation_builder.js` now understands shared `file_upload.profiles` metadata and renders separate profile-aware file inputs for shared `<parent>_assets` relations.

### Current Rules
-   Prefer the canonical shared `_assets` child relation when it is resolved; do not silently fall back to writing into legacy `_images` tables from new UI surfaces.
-   `_assets` uploads must send canonical asset metadata for each child row: `asset_kind`, `original_name`, `mime_type`, and `size_bytes`.
-   Empty shared-asset placeholder rows must not be submitted from the add-row modal. Only sections with an actual selected file should become child inserts.
-   Add-row shared attachment inputs should preserve all selected files until submit, render a visible selected-file tray, and expand one attachment selection into one child insert per file instead of keeping only a single attachment.
-   Article-view media actions should respect dataset permissions explicitly. The image gallery should hide upload/delete affordances when `/api/add-row-multipart` or `/api/delete-rows` is not allowed for the resolved child dataset.
-   Article-view attachment UX should keep upload discoverable even when the row has zero attachments: a visible dropzone/chooser hint is preferred over invisible section-level drag-and-drop alone.
-   PDF preview in the article-view attachment section should stay inline within the same article view. Reusing the global modal builder from inside attachment actions would replace the already-open article view and is therefore the wrong pattern here.
-   Previewable PDF attachments should also show a lightweight first-page thumbnail tile in the attachment row itself. Clicking the tile should reuse the same inline preview panel instead of introducing a separate modal or navigation path.
-   Big-card shared-asset attachment rows may offer inline metadata editing (`title`, `description`) when the resolved child dataset allows `/api/update-row`. Keep the original uploaded filename visible as secondary metadata even after the friendlier title changes.
-   Big-card shared-asset image rows may offer the same inline metadata editing (`title`, `description`) for the currently selected image when the resolved child dataset allows `/api/update-row`. Save those edits through one batched request instead of one field request per keystroke.
-   Attachment refreshes should be sorted deterministically (`sort_order`, then `created`, then `id`, then display name) so edit/delete flows do not become brittle around row-index assumptions.
-   Big-card image delete affordances should stay lightweight in the thumbnail itself: a small top-right `x`, a subtle primary-image toggle, and a right-click context menu for the same actions.
-   Big-card media sections should refresh through one shared `fetchDynamicChildren` -> resolver pass after asset mutations or parent-field saves. This keeps image and attachment surfaces aligned on the same shared relation metadata instead of each surface guessing separately.
-   Attachment detail surfaces should prefer attachment-linking status + `relation_kind` metadata when resolving the shared child dataset. Do not treat `_assets` suffix checks as canonical runtime truth.
-   When attachment linking status is available, prefer both `relation_kind` and `foreign_key_column` from the backend before inventing a shared child stub locally for the attachment list.
-   The article's image gallery is the one the related-rows response names (`gallery_relation`), and its main picture is the response's `card_picture`; the browser never chooses a gallery of its own. A response that names no gallery means the row has none this viewer may see, and the row's own image fields stand in only when no response arrived ([Asset_Linking_Architecture.md §4](Asset_Linking_Architecture.md#4-the-card-picture-rule)).
-   `fetchDynamicChildren` child rows may now expose `relation_kind` such as `shared_asset`, `image_asset`, or `related_rows`. Treat that backend hint as the source of truth for generic related-row/media resolution.
-   Custom-named child datasets with explicit media metadata are valid. Do not assume that real media relations must literally end with `_assets` or `_images`.
-   Generic related-row UI must not surface media relations as ordinary child tabs. Filter `relation_kind=shared_asset|image_asset` out before rendering related tabs or child-tab-config candidate lists.
